#+OPTIONS: toc:t

Your Org files are valuable — this config works to keep them saved, synced
across machines, and recoverable.

* Automatic Git sync
If your Org base directory is a Git repository, this config syncs it in the
background: it commits your changes and pushes/pulls on a timer, so your tasks
stay in step across devices without you running any Git commands.

- A small *mode-line indicator* in the file tree shows sync status. Hover it to
  see when the last successful sync happened (the date is included when it
  wasn't today), and click it to open the sync log.
- Turn it on or off with =C-c p s= (Productivity → Sync & Version Control → Git
  Sync Enabled). Turning it back on resyncs immediately.
- For manual control, =C-x g= opens [[https://magit.vc/][Magit]], the full Git interface.

The sync is intentionally quiet and won't commit while you're mid-edit. It also
recovers on its own: if a sync is ever interrupted (for example, your laptop
sleeps mid-pull), the indicator clears the stuck state and resumes by itself.
(Sync is disabled automatically when running the dev launcher — see
[[file:Developing.org][Developing & extending]].)

** When a sync fails
The indicator distinguishes trouble that will pass from trouble that needs you:

| Indicator         | Meaning                                       |
|-------------------+-----------------------------------------------|
| =✓ Sync=          | The last sync succeeded.                      |
| =↻ Syncing=       | A sync is running right now.                  |
| =⊘ Sync Off=      | You turned syncing off.                       |
| =⚠ Sync Retrying= | Out of your hands — it will try again shortly |
| =⚠ Sync Failed=   | Needs you before syncing can continue         |

/Sync Retrying/ (orange) means the remote server returned an error or the
network is unreachable. Your work is already committed locally and the next
attempt will push it, so there is nothing to do but wait.

/Sync Failed/ (red) means a merge conflict, credentials the remote refused, or
a push rejected because another device got there first. A merge conflict also
pauses syncing and opens the sync log with instructions; resolve it (=C-x g=
for Magit), then re-enable syncing.

Failures are reported *once*, as a single line at the bottom of the frame — a
server outage lasting an hour interrupts you one time, not once a minute. The
indicator carries the state from then on, and its tooltip shows what failed and
how long it has been failing. You are told once more when syncing recovers.

For the full Git output, open the sync log: click the indicator, or Productivity
→ Sync & Version Control → Show Sync Log.

* Auto-save and auto-revert
You rarely need to press save:

- *Auto-save* — Org buffers are written to disk shortly after you stop typing
  (Obsidian-style), so changes are persisted continuously.
- *Auto-revert* — if a file changes on disk (e.g. synced from another device,
  or written by the AI assistant), the open buffer refreshes to match, so you
  never edit a stale copy. This happens silently as long as you have no unsaved
  edits in that buffer. If you /do/ have unsaved edits, Emacs stops and asks
  before discarding them.

* Sessions
Your set of open files and windows is saved when you quit and restored next
time, so you pick up where you left off. The main window comes back at the size
and position you left it.

Only that one window is restored. If you had extra Emacs windows open (=C-x 5 2=
and the like), they are not reopened — otherwise a window you had long forgotten
about would reappear on the next start, showing a file you never asked for.

* Backups
Emacs keeps versioned backups and auto-save files in dedicated directories
(outside your Org folders), so an accidental change or crash is recoverable.

* Recovering blank lines lost to mobile edits
Beorg and Orgzly throw away the blank lines in your Org files when they save
them. Both read a heading as a title plus one block of text and trim the
whitespace around that block, so every blank line next to a heading disappears —
the ones between a heading and the text under it, and the ones separating a
section from the next heading. Blank lines inside a paragraph survive. Beorg can
put some back from its own settings, but only by a rule, and not where you
actually had them.

Those blank lines are still in your git history, because the automatic sync
commits whatever arrives from Dropbox. =Recover blank lines from history= (=F7=,
or Productivity → Edit Org) finds, for each file, the most recent version that
still remembers its blank lines, and works out where they belong in the file as
it is now. Headings are matched by their text and the notes under them, so a task
you ticked off on your phone is still recognised as the same task, and a task you
moved takes its spacing with it.

The report lists each file, how many blank lines would come back, which version
they came from, and the reason for every single one — whether it was remembered
from that version, or worked out from how you space the rest of your files. Where
there is nothing to go on, the file is left exactly as it is.

** Accepting what it found
Nothing is written until you say so. Most of the time you can decide straight
from the report, without opening a diff at all:

| Key | Action                                      |
|-----+---------------------------------------------|
| =1= | accept this file — put its blank lines back |
| =2= | dismiss this file, leaving it alone         |
| =A= | accept every file in the report             |
| =n= | next file                                   |
| =p= | previous file                               |
| =g= | scan again                                  |
| =+= | look one step further back in history       |
| =-= | look one step less far back                 |
| =c= | search back an exact number of commits      |
| =y= | search back an exact number of days         |
| =s= | switch how gaps with no history are handled |
| =q= | close the report, and any diff it opened    |

Each row shows the reason for every blank line it would restore, so =1= and =2=
are decisions you can make from what is already on screen. Accepting marks the
row =✓= and moves to the next, so a whole report can be worked through with
=1= =1= =1=. The report stays where it is — nothing is re-scanned under you and
you keep your place. Press =g= when you want it recomputed from disk, and =q=
to close it and put your windows back as they were.

*** Gaps with no history
Almost every blank line is copied from the older version of the file: it
remembers that there was a blank line between /these two headings/, and that is
what gets put back.

A few gaps have no such memory. If you moved a task on your phone, the two
headings that now sit next to each other were never neighbours in any version,
so nothing remembers the spacing between them; the same goes for a heading you
typed on the phone, which has never existed with its blank lines intact. Those
are the *gaps with no history*, and the last line of the report says what
happens to them. =s= switches between:

- /worked out from your style/ — count how you space the rest of your files (a
  blank line before every top-level heading, say) and apply that here.
- /left alone/ — propose nothing, so only remembered spacing is ever restored.

They are a handful of gaps per file and often none. The reason column tells you
which is which: =edge= and =half= are remembered, =rule= is worked out.

*** How far back to look
The last line of the header shows how much history is searched for a healthy
version of each file — by default the last five commits touching it, and only
those from the last day.

That is narrow on purpose. The phone writes the whole file once, when you leave
its editor, so the damage arrives as a single commit; the automatic sync commits
every minute on this side, and a file mangled on the phone is usually opened
again here the same day or the next. Looking further back costs a scan that
takes noticeably longer for versions that are no better.

Widen it when a file shows /no changes/ but you know its blank lines were fine a
while ago:

- =+= and =-= step one rung at a time, from a single commit up to a thousand.
  Both limits move together, because git applies them together: raising just the
  commit count would look like it does nothing whenever the day limit is the one
  actually binding.
- =c= asks for an exact number of commits, and =y= for an exact number of days.
  Answer =y= with =0= to drop the age limit altogether — then the commit count
  alone decides, and the header reads /any age/.

Either way the report is recomputed straight away.

** Looking at a file side by side
When you want to see a change in context, or take some of a file but not all of
it, press =d= (or =RET=, or click the file name) on a row.

Your file appears on the left as it stands now, and on the right the same file
with its blank lines back. The diff opens where the file tree was, so the
report keeps its place and its width; the tree comes back when you are done.

Everything starts accepted, because these are blank lines you had — you are
looking for the odd one you disagree with, not approving each one. Both sides
are editable, so you can work from whichever end suits you:

| Key | Action                                 |
|-----+----------------------------------------|
| =n= | next change                            |
| =p= | previous change                        |
| =b= | take this change into your file        |
| =a= | drop this change from the proposal     |
| =+= | accept every change                    |
| =x= | drop every change                      |
| =q= | done — keep what the review settled on |

If you edited the left side by hand, that is what gets saved; otherwise the
right side is. =+= and =x= reset both sides, so after either there is no
question about which one you meant. Dropping everything leaves the file
untouched rather than rewriting it with its own contents.

Whatever you decide goes back into the report. Deciding a file there with =1=
or =2= closes the diff and puts the windows back, since the comparison on
screen has just been answered.

** What it will not do
A file is saved only if you accepted something in it, and only if what you
accepted was blank lines. If a file changed since the scan — edited on another
device mid-review, or open with unsaved changes — it is skipped rather than
written, because the proposal describes the version that was scanned.

Recovery will never change a character of your text. If a review somehow leaves
one changed, saving takes an explicit confirmation.

* Under the hood / Customize
- Blank-line recovery: =lisp/ps-blank-lines.el= with =-tree=, =-engine=, =-git=
  and =-review= alongside it; settings are in =config.org= → /Settings → Blank
  line recovery/ (=ps/blank-lines-unknown-spacing= chooses what happens at gaps
  history says nothing about, =ps/blank-lines-match-floor= how alike two
  headings must be to count as the same one, and the =ps/blank-lines-ancestor-...=
  limits and step ladder how far back to look).
- Git sync: =lisp/ps-git-sync.el=; behavior is configured in =config.org= →
  /Settings → Git sync/ (=ps/git-sync-interval= and the stuck-sync
  =ps/git-sync-timeout=). Turn it off with the =PS_GIT_SYNC_DISABLE= env var or
  =ps/git-sync-paused=. Failures are sorted into classes by
  =ps/git-sync--failure-patterns=, which decides whether one shows as /Sync
  Retrying/ or /Sync Failed/; =ps/git-sync-show-log= opens the log.
- Auto-save/revert, sessions, and backups: =config.org= → /Session & Backups/
  and /Org Mode → Behavior → Auto-save .../. Reverts are driven by filesystem
  notifications rather than polling; =lisp/ps-file-notify.el= keeps a
  notification that arrives as a file is replaced (a Dropbox sync) from
  reporting an error once the revert is already done. Nothing to configure.
