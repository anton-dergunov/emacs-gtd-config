#+TITLE: Dropbox & Git together
#+OPTIONS: toc:t
#+STARTUP: inlineimages

[[file:Index.org][↑ Back to the documentation index]]

Keeping your vault in a cloud folder (Dropbox, iCloud Drive, OneDrive, Google
Drive) /and/ as a Git repository is a sensible combination: the cloud folder is
what lets you edit a file on your phone, and Git is what gives you history and
a backup you can go back through. This config's [[file:Sync-and-backups.org][automatic Git sync]] is happy
to run inside a cloud folder.

There is exactly one thing you must do first, and it is not obvious. Skip it
and the two syncs will eventually corrupt each other's work — not your notes,
but the repository itself.

* The one rule
*Only one of them may sync the =.git= folder.* Git owns Git; the cloud folder
owns your notes.

Your vault holds two very different kinds of thing. The =.org= files are
documents: if two machines change the same one, the worst case is that you
merge two versions by hand. The hidden =.git= folder is not a document — it is
a database that Git assumes only Git is writing to, on this machine, right now.

A cloud syncer does not know that. It replicates =.git= between your machines
like any other folder, and when both machines have written to it (which they do
constantly — every commit, every fetch), it does what it always does with a
collision: it keeps both versions, naming one of them =conflicted copy=.

Inside =.git= that is not a harmless extra file. Git treats every file under
=.git/refs/heads/= as a branch, so a copy landing there becomes a branch
literally named:

#+begin_example
main (Your Name's conflicted copy 2026-08-19)
#+end_example

and from that moment every Git command fails with =fatal: bad object=. Copies
of the index, the reflog and the object store are quieter but worse — those can
lose commits rather than announce themselves.

* What it looks like when it happens
- The sync indicator goes red and the sync log says
  =conflicted copies inside the repository=. Sync pauses; it will not clear on
  its own.
- Git commands in that folder fail with =fatal: bad object= or
  =did not send all necessary objects=.
- Files matching =*conflicted copy*= appear inside =.git=.

This is *not* a merge conflict, and there is nothing to resolve in Magit. Fix
it by deleting the copies and then removing the cause.

* The fix
Two ways. Both need one setup step on *every* machine that has the vault —
neither is something you do once and forget. What differs is what happens when
you forget.

Quit Emacs on all your machines first, and make sure everything is committed
and pushed (=C-x g=, or let the sync finish and check the indicator shows
=✓ Sync=). Pick one option and use it everywhere: a machine using one and a
machine using the other put different things at the same =.git= path, which is
the very collision you are trying to stop.

** Option 1 — tell Dropbox to ignore =.git=
Dropbox can be told to leave a path alone. On macOS:

#+begin_src bash
xattr -w com.dropbox.ignored 1 "/path/to/your/vault/.git"
#+end_src

On Linux:

#+begin_src bash
attr -s com.dropbox.ignored -V 1 /path/to/your/vault/.git
#+end_src

On Windows, in PowerShell:

#+begin_src powershell
Set-Content -Path 'C:\path\to\vault\.git:com.dropbox.ignored' -Value 1
#+end_src

Each machine then keeps its own private repository, and the machines exchange
history through your remote (GitHub) the way Git is meant to. Dropbox syncs
only your notes.

*This is a per-machine setting, not an account one.* It is an attribute on that
machine's filesystem; nothing about it is stored in your Dropbox account or
sent to your other computers.

What /does/ reach your other machines is the consequence: ignoring a folder
Dropbox has already synced makes Dropbox remove it from the server, so =.git=
disappears on every other machine. That looks like the setting propagated. It
did not — those machines simply lost the folder, and they have not learned to
ignore anything. So on each of them, rebuild the repository from your remote
and apply the ignore *before* Git puts anything there:

#+begin_src bash
cd /path/to/your/vault
git init
xattr -w com.dropbox.ignored 1 .git      # before anything else
git remote add origin git@github.com:you/your-notes.git
git fetch origin
git reset --mixed origin/main
#+end_src

=git reset --mixed= keeps every file exactly as it is on disk; it only tells
Git where you are in the history.

*If you forget on a machine*, that machine goes on syncing its =.git= to
Dropbox, and nothing says so. With only one machine still doing it there are no
collisions — a conflicted copy needs two writers — so the damage is a large
folder being uploaded pointlessly. But the protection is only as good as the
machine you last remembered, and adding a third computer quietly puts you back
where you started.

** Option 2 — keep the repository outside the cloud folder
Move the repository somewhere Dropbox never looks and leave a pointer behind.
Git supports this natively: =.git= may be a *file* holding a path instead of a
folder.

#+begin_src bash
cd /path/to/your/vault
mkdir -p ~/.gitrepos
mv .git ~/.gitrepos/notes-org
echo "gitdir: $HOME/.gitrepos/notes-org" > .git
git status                                # confirm it still works
#+end_src

Dropbox then syncs a one-line text file. Every machine reads the same line, so
it can never conflict — and that is also the catch:

*The path in that line must exist on every machine.* It is one shared string,
so =/Users/you/.gitrepos/notes-org= is what a Linux box will look for too, and
not find. Between machines that share a layout (same username, same OS)
this is free; across different ones you need a path that is valid everywhere,
or Option 1 instead. A relative pointer (=gitdir: ../../.gitrepos/notes-org=,
resolved from the vault) helps only if the vault sits at the same depth on
each machine, which Dropbox's own location often breaks —
=~/Library/CloudStorage/Dropbox/= on macOS against =~/Dropbox/= elsewhere.

On each further machine, either move its =.git= aside the same way, or rebuild
it from your remote.

The pointer file names the repository directory itself, so the rebuilt
repository has to sit exactly there — which is why it is created with
=git init --bare=. A plain =git init= would put it one level lower, in
=~/.gitrepos/notes-org/.git=, where the pointer would not find it. But =--bare=
also records that the repository has no working tree, and this one does have
one — your vault — so turn that back off. And a brand-new repository has no
remotes at all: =origin= is a name you have to define before it means anything.

#+begin_src bash
mkdir -p ~/.gitrepos/notes-org
cd ~/.gitrepos/notes-org
git init --bare .
git config core.bare false                 # it does have a working tree: the vault
git remote add origin git@github.com:you/your-notes.git
git fetch origin
#+end_src

Take the remote URL from a machine where the vault still works (=git remote -v=
there) or from the repository's page on GitHub. Skip that line and
=git fetch origin= reads the word =origin= as a URL, and says so:
=fatal: 'origin' does not appear to be a git repository=. Skip =core.bare=
instead and it is =git status= that fails later, with
=this operation must be run in a work tree=.

Then point the vault at the history you just fetched:

#+begin_src bash
cd /path/to/your/vault
git symbolic-ref HEAD refs/heads/main      # git init may have left HEAD on master
git reset --mixed origin/main
git branch --set-upstream-to=origin/main main
git status
#+end_src

If you are not certain your default branch is =main=, ask the remote first with
=git ls-remote --symref origin HEAD= and substitute the name it prints.

=git reset --mixed= only rewrites Git's index; your note files are left exactly
as they are on disk. Expect =git status= to come out clean if this machine's
vault matches the remote, or to list ordinary modifications if it holds edits
that were never pushed — either is fine.

One thing worth checking afterwards: whether this machine had a real =.git=
folder before the pointer file arrived from Dropbox. If Dropbox moved the old
one aside rather than replacing it, it is still sitting in the vault under a
name like =.git (conflicted copy)=. That is this machine's old history, and you
can delete it once the rebuilt repository looks right.

*If you forget on a machine*, it says so immediately and precisely. Git refuses
to do anything, naming the path it wanted —
=fatal: not a git repository: /Users/you/.gitrepos/notes-org= — and the sync
indicator turns red with /the repository this vault points at is missing/.
Syncing keeps retrying rather than pausing, so creating the missing repository
is enough to clear it — there is nothing to re-enable afterwards.

** Which one
Option 2, unless your machines have layouts too different to share one path.

Both cost the same to set up. The difference is that Option 1 fails *silently*
— a machine you skipped looks exactly like a machine you did — while Option 2
fails *loudly*, on that machine, naming what is missing. When the thing being
protected is the repository holding all your history, a mistake you can see is
worth more than one you cannot.

* Cleaning up after a collision
Delete the copies — they are copies, not your work:

#+begin_src bash
cd /path/to/your/vault
find .git -name "*conflicted copy*" -print -delete
git fsck                                  # confirm the repository is sound
#+end_src

Then re-enable syncing from *Productivity → Sync & Version Control → Git Sync
Enabled*, and do the permanent fix above so it cannot recur.

If =git fsck= reports missing objects rather than harmless "dangling" ones, the
simplest cure is to rebuild the repository from your remote with the =git init=
sequence from Option 1 — your notes on disk are untouched by any of it.

* Conflicted copies of your notes
Even with =.git= out of the way, two machines editing the same =.org= file at
the same time still produce a second file beside the original, named something
like =Plans (Your Name's conflicted copy 2026-08-19).org=. That is a
document-level collision, and it is the ordinary, recoverable kind.

This config makes sure such a file can only ever be an inconvenience:

- It is *not* committed — the vault's =.gitignore= excludes the
  =*conflicted copy*= pattern, so it never enters your history.
- It is *not* scanned — the agenda ignores it, so it cannot show you a second
  copy of every task in it.
- It *is* reported — after each sync the vault is checked, and the indicator
  shows =⚠ Conflicted Copies= when any exist. Click it for the list.

Merge whatever you need out of the copy and delete it. If you would rather not
be told, set =ps/git-sync-cloud-copy-regexp= to =nil= (see
[[file:Customization.org][Customization]]).

* Avoiding them in the first place
Nothing can prevent a collision between two machines that genuinely both wrote
the same file — a cloud folder has no locking, and keeping both versions is the
best it can do. What helps:

- Let Emacs finish saving before you close the lid. Saves here are automatic
  and near-instant, so this mostly takes care of itself.
- Prefer one "writing" machine at a time. A machine that is only *reading* your
  notes never causes a conflict, however long it stays open.
- Watch the indicator after a machine wakes up. That is when a day's worth of
  changes arrive at once.

And note the case that /is/ handled for you: if a file changes on disk while
you have unsaved edits in Emacs, your buffer is never written over it. See
[[file:Sync-and-backups.org][Sync & backups]].
